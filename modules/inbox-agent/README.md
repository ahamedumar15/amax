# inbox-agent (change 025)

Reads the Teams channels and mailboxes a tenant allows, every hour, and suggests records (opportunities, sales activities, leave, tickets) for a person to add. It never adds, sends or answers anything itself.

- **Owner:** `/modules/inbox-agent/` in `.github/CODEOWNERS`
- **Screen:** `/inbox-agent` (Operations). It leads with what needs a person (no consent, a failed scan, then the finds waiting), then four tiles (open finds, allowed sources, last scan and the next one, admin consent), "Found by agents in Teams and email" with Add, Open in chat and Dismiss, the allow-list and the recent scans. There are no forms: "Allow a mailbox or channel" and "Record admin consent" open chat, and every tile, find, row and scan is pinned. The mock has no section of its own for this screen; it follows the Presales found strip and the Integrations "Inbox agent" card.
- **Consent and the allow-list (AC-1):** the scan reads nothing until an Admin records Entra admin consent (`record_inbox_consent`), and then only the mailboxes and channels on `inbox_agent.source` (`allow_inbox_source`, `remove_inbox_source`; Admin and IT Admin). A source is read only from the moment it was allowed. Graph is asked about each allowed source by name; anything returned for another source, or from before it was allowed, is dropped.
- **Routing (AC-2):** each record type belongs to a module (`routes.ts`): an opportunity to Presales (`presales.new-opportunity`), a sales activity to Presales (`log_opportunity_activity`; Presales has no activity intent yet), leave to Leave (`leave.request`), a ticket to Helpdesk (`helpdesk.new-ticket`, dark until 022 is installed). "Add" opens chat in the owner's intent with the find pinned, so the owner's own write tool adds the record after chat's confirm. A type whose module isn't installed (no table) is never offered to the model, never suggested and never shown.
- **Suggestions (006):** each find is a `inbox-agent.route` suggestion for the person the agent acts for on that source (scope `ownerUserId`; `inbox-agent:decide@own`, Admin any), showing its source (email or Teams) and a link to the message as evidence. Accepting marks the find added; dismissing closes it. Neither writes another module's records.
- **Untrusted input (AC-5):** each message goes to the model through `think` from `@amax/agents` in 006's untrusted-input mode: the excerpt is only `data` (quoted, with the gateway's rule never to follow it), the instructions and task are fixed, no tool but `propose_suggestion` is offered, and the proposal must match the kind's schema, the find's own id and an installed record type. Mail and Teams HTML is reduced to plain text before it is stored and is rendered as text; links are kept only when https to Outlook or Teams (or a reserved `.example` host for the sandbox).
- **What is stored (AC-5, 032):** per message only an excerpt (at most 280 characters of plain text) and a link, in `inbox_agent.find`, deleted 30 days after the find closes or its suggestion expires. No sender, subject or body. The scan workflow's input and steps carry ids and counts only. The 006 suggestion holds the fields the model extracted (client, value, dates), kept per the platform's suggestion retention.
- **Credentials (AC-5, 031):** Graph is called with the `msgraph-read` credential (JSON `{ tenant, clientId, clientSecret }`), opened with `useSecret` only for the read; the token goes only in the Authorization header. Calls go through the 035 egress guards (`@amax/api/egress`: public https only, the connection pinned to the checked address, no redirects, a 2 MB cap and a 30 s timeout). A failure shows its reason on the scan, never a secret.
- **The scan (AC-3):** the `inbox-agent.scan` workflow (029) on the hourly schedule "Teams and email scan", switchable like any schedule (Settings, Workflows; and the Suggestions screen lists it as the kind's job). Insights' "Recurring agent work" switch is 026's.
- **Sandbox:** the demo tenant's consent is `sandbox`, a built-in fictional Microsoft 365 (`server/sandbox.ts`), so demo data never calls Graph. One of its messages tries to give the agent orders; the demo triage reads it as no record.
- **Contracts** (`contracts.ts`): `RECORD_TYPES`, `SOURCE_KINDS`, `SCAN_STATUSES`, `SCAN_JOB`, `SCAN_CRON`, `SUGGESTION_KIND`, `inboxState(tx)` (counts only), `EVENTS` and payload types.
- **Events:** `inbox-agent.scan.completed` (counts) and `inbox-agent.find.triaged` (ids). Handles its own `find.triaged` (makes the suggestion) and 006's `agents.suggestion.decided` (a dismissal closes the find).
- **MCP tools:** read `get_inbox_agent`, `get_inbox_find`, `get_inbox_source`, `get_inbox_scan`; write `record_inbox_consent`, `allow_inbox_source`, `remove_inbox_source`. Chat intents: allow a source, record consent.
- **Depends on** nothing but the platform (006 agents, 029 workflows, 031 secrets, 033 AI, 035 egress). **Integrates with** presales, leave and helpdesk, each optional.
- **Fixtures:** sandbox consent, 4 channels and 6 mailboxes (fictional), three scans and a failed one, and four messages: two opportunities (Adatum, Woodgrove), a leave reminder for Nimal, and the injection attempt.
- **Tests:** `pnpm --filter @amax/inbox-agent test` (DB tests need `DATABASE_MIGRATE_URL`; Graph and the model are always fakes); screen: `pnpm --filter @amax/web build && pnpm --filter @amax/inbox-agent e2e`.
