# delivery (changes 007, 008, 039, 041, 042, 044, 045, 081)

Projects, each project's board of specclaw proposals, and releases moving through each project's own environments. "Released" means a release reached the project's Prod environment; a project may have none.

- **Owner:** `/modules/delivery/` in `.github/CODEOWNERS`
- **Screens:** `/delivery` (portfolio), `/delivery/p/:key` (board + environments), `/delivery/proposals[/:phase]`, `/delivery/proposals/:key` (081: one proposal; the segment is a phase when it names one, else a key), `/delivery/releases`, `/delivery/releases/:projectKey/:version`
- **Contracts** (`contracts.ts`): `listProjectRefs`, `getProjectRef`, `managedProjectIds`, `PHASES`, `EVENTS`, `proposalHref`, and the `ReleaseDeployed` / `ProposalPhaseChanged` / `ProposalWithdrawn` / `TaskDone` / `CommitTime` payload types. 081, additive: `getProposalRef(tx, keyOrId)` (Time checks an entry's proposal with it) and `setProposalHours(tx, projectIds, totals)`, through which Time hands over approved hours per proposal for whole projects. Delivery can't read Time (Time depends on Delivery; the graph has no cycles), so this is the only writer of `proposal.hours`. `ProposalPhaseChanged` and `TaskDone` gained an optional `ownerUserId`.
- **Project creation (045, for presales' Promote):** `createProject(ctx, { key, name, client, billing, managerName?, sourceRef? })` returns `{ id, key }`, plus `existing: true` when this `sourceRef` already made this key, or `replayed: true` on an idempotency-key replay. A taken key, or a `sourceRef` that made another key, throws `ProjectConflictError` (`existingKey`, not retryable). `sourceRef` is `module.record:id` (e.g. `presales.opportunity:OPP0042`), unique per tenant in `delivery.project.source_ref`, and accepted only through the contract. Callers gate on `PROJECT_CREATE_PERMISSION` (`delivery:project:create`). Additive: earlier callers are unchanged.
- **Events:** `delivery.release.deployed`, `delivery.proposal.phase_changed`, `delivery.proposal.rekeyed`, `delivery.proposal.withdrawn` (081), `delivery.task.done`, `delivery.commit.time`
- **Notifications:** a rollback reaches the project's PMs; 081: a proposal's owner hears of a phase change or a finished task by someone else (`delivery.proposal-phase`, `delivery.proposal-task-done`); 081 amendment 1: the project's PMs hear a proposal is verified (`delivery.proposal-verified`, not for their own move; one notification per person per event)
- **MCP tools** (`mcp.ts`): read — `list_projects`, `get_project`, `list_proposals` (081: `q` search), `get_proposal` (081: one row, with tasks, stages, history and `href`), `get_proposal_metrics` (081), `get_release`, `list_environments`, `get_release_history`, `list_activity`, `get_activity`, `get_commit_time_logging`, `get_repo_sync`, `get_sync_push`; write — `create_project`, `create_proposal` (081: owner, description, card), `update_proposal`, `withdraw_proposal`, `add_proposal_task` (081), `move_proposal`, `create_release`, `tag_release`, `set_release_proposals`, `record_deployment`, `upsert_environment`, `remove_environment`, `void_deployment`, `sync_proposal`, `mark_task_done`, `set_commit_time_logging`, `sync_specclaw`, `link_project_repo`, `unlink_project_repo`
- **Chat intents** (`chat.ts`): new project, new proposal, new release, record a deployment, change a release. **Chat suggestions** (`chat-suggestions.ts`, 081): New proposal on a project's pages and the list; add a task, edit or withdraw on a hand-made proposal's page
- **Proposals made by hand (081):** an owner (the person acting by default, any active person when named), a description, an estimate, tasks added with `add_proposal_task`, and `withdraw_proposal` (a reason; never deleted; leaves its release; gone from lists, counts and boards, readable by key). A spec proposal's content and withdrawal belong to its repo; only its owner can be set in amax. A synced or pushed proposal's owner is the person it was synced for, and a later sync fills a missing owner but never replaces one.
- **081 amendment 1:** board cards and the proposal page share one action list (`ui/ProposalActions.tsx`, Time's tones: Edit primary, Withdraw a quiet link), on the card behind an Actions fold; task meters show whenever there are tasks, Proposed included; a hand-made proposal's page explains its key can move to the `-H` series; the phase bar names its month ("Released in October") and the filter says "Released, all time"; the history shows time logged against the proposal from Time's audit rows (`after.proposalId`), to the entry's owner and the project's time approvers only.
- **One filter (081):** lists, phase counts, the shipped chart and the Overview's counts never include withdrawn proposals, and include only active projects unless a project is named.
- **Viewer scopes:** contributes each user's managed projects, so `@managed` grants work
- **Ingestion (008):**
  - **Who can call it.** specclaw and CI call `sync_proposal` (with the spec's `committedAt`, 062), `mark_task_done` and `record_deployment`, as a person or as a service credential acting for one. A CI credential should be limited to those three tools (`tools` on `create_api_credential`).
  - **Pushes.** GitHub and Azure DevOps pushes arrive at `/api/webhooks/<tenant>/<provider>`. 035 verifies them (signature, replay window, dedupe) before `inbound.handle`.
  - **Attribution.** A commit counts for a person only when the provider verified it, or when its email is the verified email of their `auth.git_identity`. Such a commit closes the tasks it names (`CON-014 T3 done`). An author who isn't linked but has a person's work email becomes a `delivery.git-identity` suggestion to link them; until an Admin accepts it, that author's commits do nothing.
  - **Commit time.** A `Time: 1.5h` trailer sends `delivery.commit.time` to the time module, which drafts the hours as a suggestion on the person's own timesheet; nothing is logged until they accept. This only happens for a legal entity an Admin switched on with `set_commit_time_logging`, which needs `peopleNotified: true`. Commit data drafts timesheets only: it is never used for ratings, and nothing reads it for performance.
  - **Overview feed.** Each ingested write adds a `delivery.activity` line ("Claude for Nimal", "<credential> for Nimal", "Git for Nimal") to the Overview feed through the manifest's `activity` slot.
  - **Switching off.** With delivery off, the route finds no handler and the Overview shows no feed. With time off, the commit-time event has no reader.
- **Developer pushes (062):** the amax Claude Code plugin (`plugins/amax/`) sends a repo's specclaw state to `sync_specclaw`. amax accepts it only from the project's linked repo (`link_project_repo`, PM or Admin), and only from someone on the project (`delivery:proposal:push`). That permission doesn't open `sync_proposal`, which has none of these checks. A push from the project's default branch (`repo_default_ref`, set with the link, never by a push) covers every change; a push from another branch covers only its own change, and one naming no change is flagged. Per proposal, a push never releases, never moves back a phase, and never applies a commit older than the one the proposal was last pushed from (`proposal.synced_commit_at`). Every specclaw writer moves that mark for each proposal it read, changed or not: pushes, the 039 CLI (`delivery.proposal.mark`), and `sync_proposal`, whose `committedAt` is required. It never creates a project and never withdraws. A dry run is the push's transaction rolled back. An applied push is one audited transaction under the project's row lock, which also holds the repo check. A push with nothing new returns `unchanged`: one audit row moves the marks, and the Repo sync card gets no row. A push that changes something, or skips something a person should see (`needsReview`: anything but Released, or on a branch a step back or a stale commit), records a `delivery.sync_push` row. Each applied or refused push is a `delivery.sync_push` row, shown on the project's Repo sync card.
- **Self-sync (039, reduced by 008):** `sync/` imports a repo's `.specclaw/changes` into a project through `sync_proposal`'s service, tasks included (`pnpm --filter @amax/delivery sync:specclaw`)
- **Who owns a phase (044):** a synced proposal's phase up to Verified belongs to the repo, so `move_proposal` refuses a specclaw row. Released belongs to Prod deployments, so a sync never moves a Released proposal back (an archived change may still sync as Released). A Prod deployment records each proposal's phase before release (`deployment.prior_phases`). Voiding it puts exactly that phase back, and Verified is the fallback for records from before 044. From then on the sync follows the repo again.
- **Data:** `delivery.project` (`source_ref`: what another module created it from), `proposal`, `task` (008), `activity` (008), `commit_time` (008), `release`, `environment`, `deployment`, `weekly_stat` (task roll-ups; `project_id` null = the portfolio), `clock_pin` (all RLS on `tenant_id`); retention entries in `module.ts`
- **Charts (041):** "Tasks done per week" reads the portfolio roll-up (a missing week is a gap, not 0); "Shipped to Prod per week" counts `proposal.released_at`, the source of "Released this month". The fixtures follow fixtures.md except that series: the mock's W41 4 and W42 6 contradict its own 5 released this month, so the app shows W41 1 and W42 0. The Oct 6 "Login hotfix" is FLT's (release FLT v1.7.3), not an HRI proposal without a release: every released proposal has a release that reached Prod.
- **Today:** date windows use the tenant's `delivery.clock_pin` row when there is one (the e2e tenant pins Oct 16, 2026), else the real date.
- **Tests:** `pnpm --filter @amax/delivery test` (DB tests need `DATABASE_MIGRATE_URL`)
