# recruitment (change 023)

Open roles, candidates through the stages, offers sent for e-signature, and the hand-off of a hire to HR.

- **Owner:** `/modules/recruitment/` in `.github/CODEOWNERS`
- **Screen:** `/recruitment`. The four stats lead (open roles, candidates this quarter, time to hire, offers accepted), then the pipeline board (Applied, Screening, Interviews, Offer, Hired this quarter) with one or two cards per stage and "+N more" (`?lane=`), then the hiring funnel this quarter and hires per month. `?role=` (the role filter) narrows it all to one role. "New role" and "Add to HR" open chat ("Ask amax"); every tile, stage, card and funnel row is pinned; there are no forms.
- **Records (AC-1):** `recruitment.role`, `candidate`, `application` (one candidate for one role; the time each stage was reached is kept, so the funnel counts what happened), `interview` and `offer`. Writes are `defineService`s and MCP write tools: `open_role`, `add_application`, `move_application`, `record_interview`, `reject_application`, `send_offer`, `check_offer_signature`.
- **Candidate data (AC-1, 002):** name, email, CV and the agent's evidence are class `candidate`: only HR reads them. Admin and Leadership see the pipeline (roles, stages, counts, dates, scores) with every candidate field masked; anyone else gets a 404 and refusals. Read tools declare the fields `sensitive`, so chat redacts them per the tenant's AI policy. No event carries a candidate's name or CV.
- **Retention (032):** a candidate is anonymised twelve months after the decision (rejection or hire), the tenant default "Candidates not hired"; application notes and the agent's evidence likewise. Who sent offers and raised roles is kept seven years.
- **Screening agent (AC-2):** each new application is scored against the role's skills (rule-based, no model call) and the score is a 006 suggestion, `recruitment.screen`, whose evidence is the CV sections that matched. Accepting moves the application to screening with the score; dismissing changes nothing. No agent can reject: `reject_application` refuses anything but a person.
- **E-signature (AC-3):** `sign.ts` is the provider adapter: `{ id, label, fictional?, send(ctx, envelope), status(ctx, envelopeId) }`, registered with `registerSignProvider` from `@amax/recruitment/contracts`. **Zoho Sign** is the first: its 031 credential `zoho-sign` is JSON `{ token, templateId, dc }`, and the offer is created from that template. The **demo** provider is fictional (sends nothing, and stands in for the candidate signing). `check_offer_signature` asks the provider; a signed offer hires.
- **Hire to HR (AC-1):** a signed offer emits `recruitment.hired`. The hiring agent makes a 006 suggestion, `recruitment.hr-record`, that only someone with `hr:person:create` (HR, Admin) can accept; accepting confirms the hire for HR records (`recruitment.hire.confirmed`) and the card offers "Add to HR", which asks chat to run hr's `add_person`. hr's contract exposes no write, so the person is created by hr's own tool. When hr emits `hr.person.joined`, the hire is linked to that person (read with `getPerson` from `@amax/hr/contracts`) and the card says "Onboarding".
- **Contracts** (`contracts.ts`): `STAGES`, `STAGE_LABELS`, `CANDIDATE_FIELDS`, `listOpenRoles(reader)` (open roles and their size, never a candidate), the sign provider API, `EVENTS` and payload types.
- **Events:** `recruitment.role.opened`, `recruitment.application.received`, `recruitment.offer.sent`, `recruitment.hired`, `recruitment.hire.confirmed`. Handles its own `application.received` (screening agent) and `hired` (hiring agent), and hr's `hr.person.joined`.
- **Permissions:** HR: read, manage roles and candidates, send offers. Leadership: read. Admin holds every permission but not the `candidate` class.
- **Depends on** hr (011) and agents (006). **Integrates with** data retention (032), which is part of the platform, so there is nothing to degrade.
- **Fixtures:** three open roles (two Senior .NET openings raised by the resourcing agent from January demand on Fleet Tracker phase 2, an AI engineer, a QA engineer), this quarter's pipeline from fixtures.md (funnel 63, 41, 19, 5, 4; board 22, 9, 5, 1, 4), and a hire for each person hr's fixtures have joining May to October plus Mohamed Rifkhan (Nov 2), so hires per month match People. Candidates, CVs and emails are fictional.
- **Tests:** `pnpm --filter @amax/recruitment test` (DB tests need `DATABASE_MIGRATE_URL`); screen: `pnpm --filter @amax/web build && pnpm --filter @amax/recruitment e2e`.
