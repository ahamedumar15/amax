# onboarding (change 013)

Checklists across HR, IT and the manager when people join and leave, started by hr's events.

- **Owner:** `/modules/onboarding/` in `.github/CODEOWNERS`
- **Screen:** `/onboarding`. What needs attention leads: tickets for overdue tasks, joiners starting in the next 30 days, leavers leaving this week and open tasks, and a Needs attention card listing them. Then each person's checklist, open ones first, with its tasks grouped by owner (HR, IT Admin, the manager by name).
- **Contracts** (`contracts.ts`): `checklistsOf(personId)`, `openChecklists(kind?)`, `KINDS`, `OWNERS`, `EXIT_LINK_DAYS`, `EXIT_QUESTIONS`, `EVENTS` and the payload types
- **Events:** emits `onboarding.checklist.started`, `onboarding.task.completed`, `onboarding.checklist.completed`, `onboarding.access.requested` (`personId`, `userId`, `kind` grant or revoke, `legalEntityId`), `onboarding.exit.issued` (never the token) and `onboarding.exit.answered`. Handles `hr.person.joined` (handler `onboarding.joiner`) and `hr.person.left` (`onboarding.leaver`), acting as those jobs.
- **Templates (AC-1):** `onboarding.template` by legal entity and role (the person's department or job title; null means any), the most specific match wins. Each task goes to HR, IT Admin or the manager; a manager task goes to the person's manager by sign-in, or to HR when they have none.
- **IT access (AC-2):** 021 (it-access) isn't built. A joiner's checklist asks for a grant (due the day before they start), a leaver's for a revoke (due on their last day), as `onboarding.access.requested` for 021 to turn into a suggestion IT approves, and as an IT Admin task ("Grant/Revoke sign-in, email and licences") until then. Nothing is granted or revoked automatically; completing the task only records that IT did it. With 021 installed, its handler takes the suggestion.
- **Exit questionnaire (AC-3):** HR's `send_exit_questionnaire` makes a link (`/exit/<token>`) for a leaver's checklist. The token is 192 random bits, shown once, stored only as its keyed digest (`@amax/auth/tokens`); it works once and for 14 days, and a new link replaces an unanswered one. `exitQuestionnaire(token)` and `answerExit(token, answers)` (`server/exit.ts`) find the link by digest alone (`onboarding.lookup_exit_link`, owned by `amax_lookup` like `auth.lookup_token`), since the leaver is signed out. Answers show in `get_checklist` for HR only.
- **Gap: the public page isn't mounted.** The platform has no signed-out module route: every module route needs a session and `<module>:read`, and public paths are a fixed list in `@amax/auth/gate`. `ui/ExitPage.tsx` is ready for one (`params.token`, plus an `action` that calls `answerExit(token, exitFormAnswers(form))`); mounting it at `/exit/:token` is a platform change for its own proposal. Until then a leaver's answers can only be recorded through `answerExit`. The page takes answers in a form because the leaver has no chat, like the sign-in screen (R3).
- **MCP tools** (`mcp.ts`): read `list_checklists`, `get_checklist`, `get_checklist_task`, `onboarding_summary`; write `complete_checklist_task`, `start_checklist` (for people recorded before onboarding was installed), `send_exit_questionnaire`
- **Chat-first (R3).** The screen has no forms. Completing a task is an "Ask amax" button with the task pinned; the write runs after chat's confirm. Every ticket, card and task has a pin.
- **Permissions:** `onboarding:read` (Leadership, HR, IT Admin), `onboarding:task:complete` (HR any task in their entities, IT Admin the IT tasks), `onboarding:checklist:start` and `onboarding:exit:send` (HR). PMs and engineers who manage someone hold `onboarding:read@own` and `onboarding:task:complete@own`: in chat they see and tick off the tasks that are theirs. The screen needs the unqualified `onboarding:read`.
- **Depends on hr (011).** Integrates with it-access (021), optionally: without it the access event waits for no one and the IT Admin task carries it.
- **Data:** `onboarding.template`, `template_task`, `checklist`, `task`, `exit_link` (all RLS on `tenant_id`). People are `hr.person` ids; the checklist keeps the name so IT, who can't read hr, sees who it is. Retention entries in `module.ts`.
