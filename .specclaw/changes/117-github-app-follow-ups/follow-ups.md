- [minor B2] `modules/git-accounts/tests/setup.ts:29` The fake GitHub returns `incorrect_client_credentials` for the magic code `wrongsecret`, whatever client_id or client_secret is sent. So the AC-2 test never stores a wrong secret and drives it through the exchange; it plants the refusal by the code value. Make the fake return `incorrect_client_credentials` whenever `client_id`/`client_secret` don't match `app-id`/`app-secret-fake-…`. Then the test can store a well-formed but wrong secret (and a wrong client id) and connect with `good`. (round 1) <!-- fp:966c8c64fbc1 class:other -->
- [minor B12] `modules/git-accounts/server/app.ts:37` The `usable` cache is a process-wide Map that never evicts. Every rotation adds a new `tenant:rotatedAt` key, so it grows without limit across tenants and rotations. The `has`-then-`await`-then-`set` sequence also lets concurrent status reads (the chip and every Integrations chat-suggestion `when`) each do an audited secret use before the first one lands. Keep one entry per tenant (replace the entry when rotatedAt changes) and store the in-flight promise so concurrent reads share it. (round 1) <!-- fp:099d201e9ebb class:other -->
- [minor B12] `modules/git-accounts/server/app.ts:46` On failure the catch calls `checks.delete(ctx.tenantId)` without checking which entry it is deleting. If the credential was rotated while the read was in flight, and a newer check for the same tenant has already replaced the entry, the old read's failure deletes the newer entry. That forces an extra audited read. Delete only when the stored entry is still this one, e.g. `if (checks.get(id)?.answer === answer) checks.delete(id)`. (round 2) <!-- fp:f4e35947bdab class:other -->
- [minor B7] `modules/git-accounts/server/app.ts:50` The new guard comment says "a late failure never drops a newer check" (the `checks.get(...)?.answer === answer` comparison), but no test runs a failing read that overlaps a newer check. Deleting the comparison leaves every test green. The only effect is one extra audited read, so this is minor. Add an overlapping-check test or drop the claim. (round 3) <!-- fp:795d585ae372 class:other -->
- [minor B1] `apps/web/components/settings/GitHubAppCard.tsx:17` The `unchecked` note says 'amax couldn't read the GitHub app's credential to check it.' The spec (AC-3) also gives `unchecked` to people who don't manage credentials. For them amax never tried to read it, so on the same card the note contradicts the error line ('only those who manage credentials can check the GitHub app'). An engineer looking at a working app sees a warn chip and a claimed read failure. Fix: use a note that holds for both causes, or show only checkProblem for `unchecked`.
