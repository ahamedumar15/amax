## Open after the 5-round cap (round 5, escalated)

- [major B2, open] `packages/core/tests/secrets-ac1-datakey.test.ts` The reviewer wants a row that reads a data_key row inserted inside a savepoint through `dataKeyFor`, then rolls back, and proves it was not cached. The API never inserts a key on a caller's transaction (`secrets.data_key.create` runs in its own committed transaction), but `dataKeyFor` itself would cache a row that some other code inserted uncommitted. Closing it fully needs `dataKeyFor` to read keys only from committed state, which needs a design decision (a second connection risks pool starvation).
- [round 5, fixed without re-review] One detector (`reveals`/`redact`) for results and errors; byte and char-code lists checked in document order, even/odd interleaving and inside strings; non-JSON results refused with `SecretResultError` instead of being silently changed. The leak checker escalated in rounds 3 to 5: it is a deny-list over encodings and will always have another encoding. The structural alternative is for connectors to receive the value only inside an adapter that makes the HTTP call (useSecret returns the response, never sees the value in user code).
