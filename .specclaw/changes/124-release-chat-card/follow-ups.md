- [minor B1] `apps/web/lib/in-app.ts:1` `inApp` rejects only `//` and `/\` straight after the leading slash. Browsers strip tab, CR and LF from URLs, so `/\t/evil.example` passes this check and becomes `//evil.example`, a different host. The test says "never another host" but covers only two spellings. Fix: reject any control character or whitespace too (e.g. `/^\/(?![/\\])[^\s\x00-\x1f]*$/`), or resolve with `new URL(url, base)` and compare the origin. Add those variants to the test. - [major B6] `modules/delivery/server/release-proposals.ts:19` `openElsewhere` only counts another release as holding a proposal while that release is not completed. So a Verified proposal that sits in a completed release is listed on the card with no detail and no "Move from their release" box. Both writers then quietly take it out of that completed release, with no `reassign` needed. 123 says a completed release can't change (it refuses `set_release_proposals` and `tag_release`), yet this changes what the completed release contains. Fix: treat membership of a completed release as `shippedElsewhere`, or at least require `reassign` for it too, the same as for an open release. Show the same detail on the card. - [minor B6] `apps/web/components/chat/form-values.ts:66` `valueOf` drops ticked keys that are not among the shown options. A proposal key that the model or user put in the draft and that isn't eligible (Building, withdrawn, shipped, or a typo) disappears on confirm and is never refused. The person sees an unticked list and a release created without that proposal. Fix: in `proposeRelease`, check the draft's `proposalKeys` against the eligible list for the starting input so the refusal shows on the field, or keep unknown keys so the service refuses them.
